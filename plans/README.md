# Delore — Apple-style motion/material plans

Generated by a full-codebase `improve-animations` audit at commit `b1c6223`,
scoped to the user's explicit request: all 8 HIGH-severity findings, plus a
dedicated token-consistency pass. See the audit summary in chat for the
full findings table (46 total: 8 HIGH, 20 MEDIUM, 18 LOW) — only the
selected subset became plans below.

## Rejected findings (not planned — false positives)

Two findings from the raw audit were re-vetted and rejected before writing
any plan, per the "don't re-litigate settled decisions" rule:

- **`lib/common/navigator.dart`** — flagged for not using `RouteXMotion`
  tokens. On inspection, this file is a faithful hand-port of Flutter's own
  Cupertino page-transition physics (`Curves.fastEaseInToSlowEaseOut`,
  `linearToEaseOut`, `easeInToLinear` are the exact curves
  `CupertinoPageTransitionsBuilder` uses internally, plus a matching edge
  shadow). Consolidating it onto `RouteXMotion.curve` would replace
  authentic iOS push/pop physics with a generic snap — a regression against
  this effort's own goal. Left untouched.
- **`lib/widgets/tab.dart`** — spring constants
  (`SpringDescription(mass: 1, stiffness: 503.551, damping: 44.8799)`,
  `_kMinThumbScale = 0.95`) flagged for not matching `RouteXMotion`. These
  are copied from `CupertinoSlidingSegmentedControl`'s own private
  implementation — deliberate, not ad-hoc. Only this file's *missing
  reduced-motion gate* was planned (003); the physics themselves are
  correctly out of scope.

**Note on 004**: as written, this plan called `MediaQuery.maybeOf(context)`
inside `initState()` — invalid in Flutter (inherited-widget lookups can't
happen before `initState` completes). Fixed during execution by reading
reduced motion via `WidgetsBinding.instance.platformDispatcher.accessibilityFeatures.disableAnimations`
instead (no `BuildContext` needed, same pattern used in plan 008's Site E).
Future plans authored by this skill should default to that pattern
whenever a reduced-motion check needs to happen in `initState`.

## Recommended execution order

1. **001–007 (HIGH, in any order)** — each is a single, independent file.
   No dependencies between them. Safe to execute in parallel if using
   multiple agents/sessions.
2. **008** — after 001–007, since two of its sites (Site D in
   `applications_workspace.dart`) sit in the same file as unrelated
   MEDIUM findings noted-but-not-planned; doing the HIGH plans first
   avoids compounding diffs in files touched twice.
3. **009 last** — purely cosmetic token references, zero risk of
   conflicting with 001–008's behavioral changes, but touches the largest
   number of files (9) so is easiest to review in isolation once the
   higher-leverage fixes have already landed.

## Notes for whoever executes these

- Every plan is self-contained — file paths, current-code excerpts, and
  exact target values are all inline. No plan assumes knowledge of the
  audit conversation.
- Every plan was written against commit `b1c6223`. If the target repo has
  moved since, expect some drift — each plan's Boundaries section says to
  stop and report rather than improvise past a mismatch.
- Two plans (002, 003) explicitly protect deliberately-ported Apple/iOS
  physics from earlier findings that tried to "consolidate" them onto
  generic tokens — the framework file `lib/widgets/tab.dart`'s spring
  constants and `lib/common/navigator.dart`'s Cupertino curves are correct
  as-is and must not be touched by any future audit pass either, unless the
  goal is to deliberately change that physics.
- After executing any plan, run it back through `review-animations` (the
  companion skill) before considering it done — this audit's own Hard
  Rules require a reviewed diff, not just a mechanically-applied plan.
